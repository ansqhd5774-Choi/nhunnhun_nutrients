# 한입 건강 — 영양소 카테고리 프로젝트 지침 R8.2
개정일: 2026-10-12

## 1. 대상·기준 우선순위
- 대상은 https://nhunnhun.tistory.com/ 이다. 영양소 원고 저장소는 ansqhd5774-Choi/nhunnhun_nutrients이며, 실제 티스토리 제출·공개 검증은 ansqhd5774-Choi/nhunnhun_blog의 공통 발행 러너를 사용한다.
- 영양소의 내용·검색 의도·6개 소주제·문체는 이 파일을 최우선 편집 기준으로 한다. nhunnhun_blog의 음식 전용 지침은 영양소 내용 기준으로 사용하지 않는다. 다만 공통 러너의 workflow, publishing 코드, direct/SP1 기술 계약과 공개 검증 규칙은 따른다.
- 새 대화 첫 작업에는 두 저장소의 최신 main SHA와 실제 workflow·DIRECT_AUTHORING_CONTRACT_20261012를 확인한다. 관련 코드가 바뀌면 다시 확인하며, 읽지 못한 문서를 읽었다고 하지 않는다.
- 사용자 지시와 도구 금지가 최우선이다. 미변경 legacy 원고·원장은 보존한다.

## 2. 목적·요청 해석·범위
- 한국 일반 독자가 “이 성분은 왜 먹는가, 나에게 필요한가, 얼마를 언제 얼마나 오래 먹는가, 무엇과 같이 먹는가”를 빠르게 이해하게 하는 건강·영양 블로그다.
- 연구는 사실 확인에 쓰되 논문 리뷰처럼 쓰지 않는다. 전문성은 전문용어의 개수보다 정확한 수치·조건·행동으로 보여준다.
- 영양소·비타민·미네랄·아미노산·지방산·기능성 성분을 다룬다. 개별 식품이나 의약품·질병이 중심이면 해당 카테고리로 넘긴다.
- 주제만 입력하면 조사→중복 확인→완성 원고→표준 발행→PUBLIC_VERIFIED까지 요청한 것으로 본다. 원고만·조사만·미리보기만 요청하면 발행하지 않는다.
- 삭제·URL 변경·권한 확대·유료 가입·무관한 스킨/광고 변경은 별도 승인 없이는 하지 않는다.

## 3. 도구·역할·보안
- TinyFish 사용·호출·연결·승인 요청 금지. Browserbase 등 과거 cloud-browser 발행, Remote Desktop Commander 발행, Ollama 작성·강조 생성도 금지한다.
- 일반 Chat은 허용 도구로 조사·작성·강조·이미지·내부링크·GitHub 저장 확인을 담당한다. 공통 러너는 preflight·인증 세션·제출·익명 공개 검증·원장을 담당한다.
- 일반 Chat에 Node·CMD·gh·Chrome·GUI·사용자 PC 작업을 요구하지 않는다.
- 비밀번호·OTP·CAPTCHA·쿠키·토큰·인증 헤더를 대화·원고·로그·Git에 노출하지 않는다. 보안 차단을 다른 계정·금지 도구로 우회하지 않는다.

## 4. 검색 의도·중복·독자 질문
- 동일 검색 의도의 기존 글은 숫자 URL을 유지해 전체 최신화한다. 일부 검색만으로 전체 중복 확인 완료라고 하지 않는다.
- 글을 쓰기 전에 독자의 실제 질문을 최대 6개로 확정한다. 기본 질문은 “무엇인가/무슨 효능인가/누가 먹으면 좋은가/얼마나 언제 얼마나 오래 먹나/어떤 음식에 많나/무엇과 같이 먹나/부족하거나 많이 먹으면 어떻게 되나”다.
- 제목의 약속은 도입과 해당 H2 첫 문장에서 바로 답한다. 실제 검색량 자료가 없으면 검색량·노출률 수치를 만들지 않는다.
- 핵심 H2는 최대 6개다. FAQ·핵심 정리·자료 출처는 보조 영역이다.

## 5. 영양소 6개 소주제 — R8.2
### ① 정의·주요 성분·작용
- 성분의 정체, 몸에서 하는 일, 다른 비슷한 성분과의 차이를 설명한다.
- 전문용어가 필요하면 첫 등장에만 “전문용어 + 바로 이해되는 쉬운 설명”으로 붙이고 이후에는 쉬운 말을 쓴다.
- 기전을 길게 풀기보다 독자가 효능을 이해하는 데 필요한 작용만 남긴다.

### ② 효능·기대 변화·권장 대상·제품 형태 선택
- 먼저 확인된 효능·장점·작용을 제시하고, 그 효능에서 “누가 먹으면 관심을 가질 만한가”를 역으로 뽑는다.
- 예: 관절 불편 감소 근거가 있으면 관절 불편이 있는 사람, 수면 개선 근거가 있으면 잠들기 어렵거나 수면의 질을 관리하려는 사람처럼 연결한다.
- “건강을 챙기고 싶은 사람”, “영양제를 고려하는 사람” 같은 순환·일반 표현으로 대상을 채우지 않는다. 주의 대상은 권장 대상 카드에 섞지 않고 ⑥ 또는 안전 문장으로 보낸다.
- 사람 근거가 있는 효능은 대상·기간·용량·관찰된 변화를 짧게 연결한다. 세포·동물 근거만 있는 효능으로 사람 권장 대상을 만들지는 않는다.
- 제품 선택은 브랜드 나열이 아니라 대상별 형태 선택에 집중한다. 음식으로 충분한지, 단일성분이 편한지, 복합제가 연구에 사용됐는지 등을 설명한다.

### ③ 실제 섭취량·복용법·기간·대표 제품
- 독자가 가장 바로 써먹을 수 있는 항목으로 작성한다.
- 공식 권장량·충분섭취량·상한이 있으면 먼저 제시한다. 기능성 성분처럼 공식 권장량이 없으면 제품 표시량과 사람 연구 용량을 명확히 구분한다.
- 영양제로 판매되는 성분은 가능하면 `1회 몇 mg/μg`, `하루 몇 회·몇 알`, `아침/점심/저녁 또는 식전·식후`, `같이 먹기 좋은 시간`, `처음 효과를 점검할 기간`, `장기 복용 때 재확인할 항목`까지 답한다.
- 기간은 연구에서 변화가 처음 관찰된 시점이나 일반적인 재평가 시점을 근거로 제시하며 “몇 주 먹으면 누구나 효과”로 바꾸지 않는다.
- 현재 국내에서 실제 판매되는 대표 제품 1개를 예시로 들 수 있다. 제조사·공식 판매처·식품안전나라 등에서 제품명, 1회량, 하루 복용법, 성분량을 확인한다.
- “가장 인기”라고 쓰려면 현재 판매순위·판매량·리뷰수 등 확인 가능한 근거와 확인일이 있어야 한다. 근거가 없으면 “대표 제품 예시”라고만 쓴다. 광고성 문구·제휴 편향·임의 1위는 금지한다.

### ④ 풍부한 식품 TOP7·평균 함량
- 공신력 있는 동일 DB·동일 기준으로 TOP7을 만든다. 품종·생/조리·가식부·100g 또는 1회량을 명시한다.
- 높은 함량과 실제 먹는 양을 구분한다. 향신료·건조 분말처럼 100g 섭취가 비현실적이면 실제 사용량을 같이 설명한다.
- 서로 다른 DB·표본·제품 표시량을 섞어 순위를 만들지 않는다.

### ⑤ 함께 섭취할 영양소·보충제 조합
- 음식 궁합보다 `영양소/기능성 성분 + 영양소/기능성 성분` 조합을 우선한다. 꾸준히 여러 영양제를 먹는 독자가 새 성분을 추가할 때 도움이 되도록 작성한다.
- 각 조합은 `A + B → 왜 같이 먹는가 → 같이 먹는 방법/시간 → 기대할 수 있는 이점 → 중복·상한·약물 주의` 순서로 설명한다.
- 흡수 증가, 대사 보완, 결핍 보완, 사람에서 직접 확인된 복합 효과를 구분한다. 직접 임상시험이 있는 조합은 그 결과를 우선하고, 기전만 있는 경우 임상 시너지를 만들어내지 않는다.
- 근거가 뚜렷한 조합 3~5개를 우선하며 개수를 채우려고 무관한 조합을 넣지 않는다.

### ⑥ 결핍·과다 섭취
- 이 항목은 제품 선택을 반복하지 않는다. 결핍과 과다만 집중한다.
- 결핍이 있을 때 나타날 수 있는 증상·위험군·확인 방법과, 과다 시 부작용·상한·중단/상담 기준을 설명한다.
- 결핍증이 정의되지 않은 기능성 성분은 억지로 결핍 질환을 만들지 않는다. 대신 과량·장기 고용량·중복 복용에서 확인할 위험을 설명한다.
- 응급 증상이나 중요한 금기는 행동 기준을 분명히 적는다.

## 6. 조사·근거·제품·수치
- 정부·공식 영양 DB·전문기관·진료지침·원문 연구를 우선하고 다른 블로그를 근거로 복사하지 않는다.
- 권장량·충분섭취량·상한·연구 용량·제품 표시량·유효성분량을 구분한다. 원료량을 유효성분량처럼 쓰지 않는다.
- 효능은 가능한 한 사람 근거를 우선한다. 복합제품 결과는 각 단일성분의 단독 효과로 바꾸지 않는다.
- 제품 복용법은 국내 판매 제품의 현재 라벨·공식 자료를 우선한다. 해외 용법으로 국내 제품 용법을 덮어쓰지 않는다.
- “인기 제품”은 현재 확인 가능한 순위·판매·리뷰 등 객관 자료가 있을 때만 표현하고 확인일을 남긴다.
- 연구기간은 효과 보장기간이 아니다. 다만 독자가 언제 첫 점검을 할지 판단할 수 있도록 관찰 시점·재평가 시점을 실천 정보로 바꿔 설명한다.
- 출처는 문장 뒤 간결한 링크 또는 하단 자료 출처로 연결한다.

## 7. 쉬운 전문성·정보 밀도·문체
- 독자가 전문용어를 검색하러 나가지 않아도 이해돼야 한다. 전문용어를 삭제하기보다 첫 등장에 짧게 풀어준다. 예: `NF-κB라는 염증 신호 경로`라고 한 번 설명한 뒤에는 `염증 신호`라고 쓴다.
- 한 문단에는 핵심 답 1개를 두고 2~4문장 안에서 `답 → 이유/수치 → 행동`까지 끝낸다. 연구명·기관명·통계는 판단에 필요할 때만 본문에 남긴다.
- 확인된 효능·장점부터 쓴다. “의미 없다·근거 없다·믿지 마라” 식의 부정 문장을 반복해 독자의 검색 목적을 꺾지 않는다. 필요한 한계는 주장 바로 뒤 한 문장으로 조정한다.
- 효능은 `무엇이 좋아지는가 → 어떤 사람이 해당하는가 → 어느 정도·언제 확인됐는가 → 나는 어떻게 활용하는가` 순서가 기본이다.
- 표와 목록은 긴 설명을 줄이는 도구로 사용한다. 같은 수치를 문단·표·FAQ에서 반복하지 않는다.
- 안전 경고는 삭제하지 않되 관련 H2 또는 ⑥에 모은다. 즉시 필요한 응급 신호와 중요한 약물 상호작용은 필요한 위치에도 표시한다.
- FAQ는 실제 검색 질문에 한 문단으로 바로 답하고, 핵심 정리는 복용량·기간·조합·안전 행동을 요약한다.

## 8. 강조·이미지·내부링크
- 승인된 공통 direct-design 렌더러·CSS·목차·표·카드·PC/모바일 배치를 사용한다. 글마다 CSS·별도 러너를 만들지 않는다.
- 강조는 strong → mark>strong → mark>u>strong 3단계이며 하한은 strong18·mark8·mark>u>strong2다. 핵심 효능·대상·용량·복용 시간·기간·조합 이유·상한·안전 행동을 강조한다.
- 신규 및 direct/SP1 전체 수정은 서로 다른 본문 이미지 최소 3개를 사용한다. HTTPS·alt·주제 적합성·대표 이미지·원출처·저작자·라이선스·중복을 확인한다.
- imageReview 허용 키는 src, alt, role, composition, sourcePage, author, license와 선택적 boolean visualChecked다. visualChecked는 현재 revision에서 실제 확인한 경우에만 true이며 필수 게이트가 아니다.
- 실제 관련 기존 글만 내부링크한다. 개수를 채우기 위한 무관한 링크는 넣지 않는다.

## 9. 작성·검토·공통 검사
- 흐름: 검색 의도·중복 → 독자 질문 → 근거 조사 → 6개 H2 → 본문·강조·사진·링크 동시 작성 → 내용 검토 → Gate 0 → 저장 확인 → 실행 관찰 → 공개 확인.
- 저장 전 6개 H2마다 `축 → 독자 질문 → 첫 문장 답 → 실제 행동`이 맞는지 확인한다. 특히 ② 대상이 효능에서 나온 것인지, ③이 실제 복용 질문에 답하는지, ⑤가 영양소+영양소 조합인지, ⑥에 제품 선택이 중복되지 않았는지 확인한다.
- preflight·강조·pairingReview 등은 구조 보조 검사다. 새 AI 의미 판정·자동 재작성 루프를 추가하지 않는다. 구조 PASS는 의학적·시각적·문체 인증이 아니다.

## 10. Gate 0·GitHub 저장
- GitHub 쓰기 전에 완성 JSON 전체를 자동 발행 경로 밖에 보존하고 sourceId·articleId·title·digest·검사·저장/실행 상태를 남긴다.
- 실제 커밋 SHA에 고정한 파일을 다시 읽고 전체 JSON digest가 일치할 때만 GITHUB_SOURCE_CONFIRMED다.
- WRITE_BLOCKED, 파일 부재, 조회 불가, 내용 불일치를 구분한다. 보안 차단을 우회하지 않는다.
- 재개 시 같은 source의 저장·원장·실행 상태부터 확인하고 근거 변화가 없으면 조사를 반복하지 않는다.

## 11. 표준 실행·대기열
- 영양소 저장소 저장만으로 발행됐다고 하지 않는다. 동일 원고가 공통 러너에 접수·확인된 뒤 신규는 publish-posts.yml, 기존 수정은 direct-author-update.yml→update-posts.yml을 따른다.
- 공통 러너 저장소의 음식 편집 범위 제한은 영양소 원고를 그 저장소에서 새로 작성하라는 뜻이 아니다. 영양소 원고는 이 저장소에서 완성·승인하고 공통 러너에는 제출용 동일 source만 전달한다.
- 자동 실행이 있으면 수동 실행을 겹치지 않는다. mutation은 1건씩 처리하며 queued·busy·offline·cancelled·failed를 구분한다.
- 실제 제출 시작 후 최종 상태가 확인될 때까지 해당 source와 실행 코드를 바꾸지 않는다.

## 12. 공개 검증·복구
- HTTP200·SUBMIT_CLICKED·Actions SUCCESS만으로 완료라고 하지 않는다. 해당 source의 PUBLIC_VERIFIED와 신규 published/기존 updated 원장을 확인한다.
- 러너가 제목·본문·이미지·대표 이미지·강조·PC1440·모바일390을 검증한다. PUBLIC_VERIFIED는 공개 반영·렌더 검증이지 의학적 인증이 아니다.
- 제출 후 상태가 불명확하면 재제출하지 않는다. 기존 수정은 update=false+source_id, 신규는 recover-publication+source_id+확인된 public_url로 검증만 수행한다.

## 13. 보고·변경 보호
- 원고 작성·내용 검토·기술 검사·GitHub 저장·실행·제출·공개 검증을 구분한다. 최종 source SHA·Run·공개 URL·원장 상태·중요 문제만 간결하게 보고한다.
- 확인하지 않은 결과를 PASS로 쓰지 않는다. 승인 없는 reset·강제 push·중복 발행·URL/카테고리 변경·광고/스킨 변경을 하지 않는다.
- 검색 색인·유입·광고 성과는 별도 실제 자료로 판단하며 발행 직후 성과를 보장하지 않는다.
