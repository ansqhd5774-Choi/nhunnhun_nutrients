# 한입 건강 — 영양소 카테고리 프로젝트 지침 R8.13

## 1. 대상·기준 우선순위

- 영양소의 내용·검색 의도·6개 소주제·문체·상단 핵심 요약 구성은 이 파일을 최우선 편집 기준으로 한다. nhunnhun_blog의 음식 전용 지침은 영양소 내용 기준으로 사용하지 않는다. 다만 공통 러너의 workflow, publishing 코드, direct/SP1 기술 계약과 공개 검증 규칙은 따른다.

## 2. 목적·요청 해석·범위
- 한국 일반 독자가 “이 성분은 왜 먹는가, 나에게 필요한가, 얼마를 언제 얼마나 오래 먹는가, 무엇과 같이 먹는가”를 빠르게 이해하게 하는 건강·영양 블로그다.
- 연구는 사실 확인에 쓰되 논문 리뷰처럼 쓰지 않는다. 전문성은 어려운 용어의 개수보다 정확한 수치·조건·행동을 짧게 전달하는 데서 보여준다.
- **독자에게 보여주는 말은 연구자가 쓰는 말보다 한국 일반 독자가 실제로 아는 말을 우선한다.** 정확성을 해치지 않는다면 `일반 마늘·흑마늘·발효 마늘`, `눈 건강`, `혈압 관리`처럼 검색·일상에서 쓰는 표현을 먼저 사용한다.
- 영양소·비타민·미네랄·아미노산·지방산·기능성 성분을 다룬다. 개별 식품이나 의약품·질병이 중심이면 해당 카테고리로 넘긴다.
- 주제만 입력하면 조사→중복 확인→완성 원고→표준 발행→PUBLIC_VERIFIED까지 요청한 것으로 본다. 원고만·조사만·미리보기만 요청하면 발행하지 않는다.
- 삭제·URL 변경·권한 확대·유료 가입·무관한 스킨/광고 변경은 별도 승인 없이는 하지 않는다.

## 3. 도구·역할·보안
- TinyFish 사용·호출·연결·승인 요청 금지. Browserbase 등 과거 cloud-browser 발행, Remote Desktop Commander 발행, Ollama 작성·강조 생성도 금지한다.
- 일반 Chat은 허용 도구로 조사·작성·강조·이미지·내부링크·GitHub 저장 확인을 담당한다. 공통 러너는 preflight·인증 세션·제출·익명 공개 검증·원장을 담당한다.
- 일반 Chat에 Node·CMD·gh·Chrome·GUI·사용자 PC 작업을 요구하지 않는다.
- 비밀번호·OTP·CAPTCHA·쿠키·토큰·인증 헤더를 대화·원고·로그·Git에 노출하지 않는다. 보안 차단을 다른 계정·금지 도구로 우회하지 않는다.

## 4. 검색 의도·중복·독자 질문
- 동일 검색 의도의 기존 글은 숫자 URL을 유지해 전체 최신화한다. 일부 검색만으로 전체 중복 확인 완료라고 하지 않는다.
- **기존 글 전체 최신화에서 유지하는 것은 숫자 URL·articleId와 현재도 유효한 사실·출처 자산뿐이다. 기존 H2 순서·소제목 문구·문단 배열을 새 원고의 골격으로 사용하지 않는다.** 기존 문장은 최신 근거로 다시 확인된 사실 단위에서만 참고할 수 있으며, 문단이나 구조를 통째로 승계하지 않는다.
- **전체 최신화는 먼저 이 문서의 ①~⑥에 맞는 빈 H2 골격을 만든 뒤 최신 조사 결과를 그 골격에 배치한다.** 검색 의도에 맞게 H2 문구를 자연스럽게 다듬을 수는 있지만 각 H2가 담당하는 ①~⑥의 역할은 바꾸지 않는다. 사용자가 소주제 문구나 배열을 직접 지정한 경우 그 지시를 우선한다.
- 글을 쓰기 전에 독자의 실제 질문을 최대 6개로 확정한다. 기본 질문은 “무엇인가 / 무슨 효능인가 / 누가 먹으면 좋은가 / 얼마나·언제·얼마나 오래 먹나 / 어떤 음식에 많나 / 무엇과 같이 먹나 / 부족하거나 많이 먹으면 어떻게 되나”다.
- 제목의 약속은 도입과 해당 H2 첫 문장에서 바로 답한다. 실제 검색량 자료가 없으면 검색량·노출률 수치를 만들지 않는다.
- 핵심 H2는 최대 6개다. FAQ·자료 출처는 보조 영역이다.
- 신규 및 전체 수정은 대표 이미지와 짧은 도입 뒤, 첫 H2보다 앞에 승인된 `핵심만 먼저` 6카드 요약을 둔다. 하단의 별도 `핵심 정리` H2는 만들지 않는다.

## 5. 영양소 6개 소주제

### ① 정의·주요 성분·작용
- 성분의 정체, 몸에서 하는 일, 비슷한 성분과의 차이를 설명한다.
- 전문용어가 필요하면 첫 등장에만 “쉬운 한국어 설명 + 필요할 때 전문용어를 괄호” 순서로 붙이고 이후에는 쉬운 말을 쓴다.
- 기전을 길게 풀기보다 독자가 효능을 이해하는 데 필요한 작용만 남긴다.

### ② 효능·기대 변화·권장 대상·제품 형태 선택
- 먼저 확인된 효능·장점·작용을 제시하고, 그 효능에서 “누가 먹으면 좋은가”를 역으로 뽑는다.
- 예: 관절 불편 감소 근거가 있으면 관절 불편이 있는 사람, 수면 개선 근거가 있으면 잠들기 어렵거나 수면의 질을 관리하려는 사람처럼 연결한다.
- “건강을 챙기고 싶은 사람”, “영양제를 고려하는 사람”, “제품을 선택하려는 사람” 같은 순환·일반 표현으로 대상을 채우지 않는다. 주의 대상은 권장 대상 카드에 섞지 않는다.
- 권장 대상은 확인된 효능과 사람 연구 대상에서 직접 도출한다. 특정 하위군에서만 변화가 관찰됐다면 그 조건을 대상 표현에 남기고 일반 성인 전체로 넓히지 않는다.
- 사람 근거가 있는 효능은 대상·기간·용량·관찰된 변화를 짧게 연결한다. 세포·동물 근거만 있는 효능으로 사람 권장 대상을 만들지 않는다.
- 제품 형태 선택은 음식·단일성분·복합제 중 어떤 형태가 목적과 근거에 맞는지 설명한다. 같은 이름의 성분이라도 원료·구조·인정 기능이 다르면 목적별 제품 형태와 섭취량을 분리한다.

### ③ 실제 섭취량·복용법·기간·대표 제품
- 독자가 가장 바로 써먹을 수 있는 항목으로 작성한다.
- 공식 권장량·충분섭취량·상한이 있으면 먼저 제시한다. 기능성 성분처럼 공식 권장량이 없으면 제품 표시량과 사람 연구 용량을 명확히 구분한다.
- 영양제로 판매되는 성분은 가능하면 `1회 몇 mg/μg`, `하루 몇 회·몇 알`, `아침/점심/저녁 또는 식전·식후`, `같이 먹기 좋은 시간`, `처음 점검할 기간`, `장기 복용 때 재확인할 항목`까지 답한다.
- 첫 점검 시점은 실제 사람 자료에서 변화가 관찰된 시점 또는 해당 인체적용시험의 관찰기간을 우선 사용한다. 임의로 8~12주 같은 범위를 만들지 않으며, 연구기간은 효과 보장기간이 아니라고 분명히 한다.
- 현재 국내에서 실제 판매되는 대표 제품 1개를 예시로 들 수 있다. 제조사·공식 판매처·식품안전나라 등에서 제품명·1회량·하루 복용법·성분량을 확인한다.
- 대표 제품은 작성 시점에 공식 판매 페이지나 공식 제품 정보가 실제로 살아 있는지 확인한다. 소비기한·재고·리뉴얼 정보가 현재 페이지에 표시돼 있으면 최신 판매 확인의 보조 근거로 활용하되, 특정 로트 정보는 전체 제품의 영구 정보처럼 쓰지 않는다.
- “가장 인기”라고 쓰려면 현재 판매순위·판매량·리뷰수 등 객관 자료와 확인일이 있어야 한다. 근거가 없으면 “대표 제품 예시”라고만 쓴다.

### ④ 풍부한 식품 TOP7·평균 함량
- 공신력 있는 동일 DB·동일 기준으로 TOP7을 우선 만든다. 품종·생/조리 상태·가식부·100g 또는 1회량을 명시한다.
- **TOP7은 목표이지 절대 개수 규칙이 아니다. 동일 기준으로 7개를 확보하지 못하면 TOP5, 그마저 부족하면 TOP3로 자연스럽게 줄인다.** 3개도 같은 기준으로 비교하기 어렵다면 순위 없이 `확인 가능한 식품과 함량`으로 설명한다.
- 숫자를 채우려고 익명 제품 번호, 서로 다른 DB·단위, 일반 독자가 식품으로 인식하기 어려운 실험 시료를 끼워 넣지 않는다.
- 동일 원문 연구의 가공 형태를 비교할 때도 **본문·H2·표에는 정확성을 유지하는 범위에서 대중이 아는 한국어 이름을 우선한다.** 예를 들어 연구용 가공명·균주명보다 `일반 마늘·말린 마늘·발효 마늘·흑마늘·숙성 흑마늘`처럼 실제 독자가 이해하는 이름을 쓴다. 단, 실제 시료가 흑마늘이 아닌데 흑마늘이라고 바꾸는 식의 부정확한 치환은 하지 않는다.
- 전문 가공법·균주·학명이 결과 해석에 꼭 필요하면 표의 주 이름이 아니라 가까운 설명이나 출처에서 한 번만 보조한다.
- `평균 함량`이라고 쓸 때는 실제 평균값 또는 동일 연구의 mean±SD 등 평균 자료여야 한다. 최소 규격·허용 기준·제품 표시 최저값은 평균 함량으로 부르지 않는다.
- 높은 함량과 실제 먹는 양을 구분한다. 향신료·건조 분말처럼 100g 섭취가 비현실적이면 실제 사용량도 같이 설명한다.
- 서로 다른 DB·표본·제품 표시량을 섞어 순위를 만들지 않는다.

### ⑤ 함께 섭취할 영양소·보충제 조합
- 음식 궁합보다 `영양소/기능성 성분 + 영양소/기능성 성분` 조합을 우선한다. 꾸준히 여러 영양제를 먹는 독자가 새 성분을 추가할 때 도움이 되도록 작성한다.
- 각 조합은 `A+B → 왜 같이 먹는가 → 같이 먹는 방법·시간 → 기대 이점 → 중복·상한·약물 주의` 순서로 설명한다.
- 흡수 증가·대사 보완·결핍 보완·사람에서 확인된 복합 효과를 구분한다. 직접 사람 연구가 있는 조합을 우선하고, 기전만 있는 경우 임상 시너지를 만들어내지 않는다.
- 직접 사람 연구가 있는 조합은 `같이 먹은 전체 조합에서 확인된 결과`로 표현하고 단일성분 각각의 독립 효과로 바꾸지 않는다.
- 근거가 뚜렷한 조합 3~5개를 우선하되, 실제로 강한 조합이 1~2개뿐이면 그 수만 제시해도 된다. 개수를 채우기 위해 비타민 C·D·아연·오메가3처럼 주제 성분과 직접 복합 근거가 약한 조합을 억지로 추가하지 않는다.

### ⑥ 결핍·과다 섭취
- 이 항목은 제품 선택을 반복하지 않는다. 결핍과 과다에 집중한다.
- 결핍이 있을 때 나타날 수 있는 증상·위험군·확인 방법과, 과다 시 부작용·상한·중단/상담 기준을 설명한다.
- 결핍증이 정의되지 않은 기능성 성분은 억지로 결핍 질환을 만들지 않는다. 대신 과량·장기 고용량·중복 복용에서 확인할 위험을 설명한다.
- 응급 증상이나 중요한 금기는 행동 기준을 분명히 적는다.

## 6. 조사·근거·제품·수치
- 정부·공식 영양 DB·전문기관·진료지침·원문 연구를 우선하고 다른 블로그를 근거로 복사하지 않는다.
- 권장량·충분섭취량·상한·연구 용량·제품 표시량·유효성분량을 구분한다. 원료량을 유효성분량처럼 쓰지 않는다.
- 효능은 가능한 한 사람 근거를 우선한다. 복합제품 결과를 각 단일성분의 단독 효과로 바꾸지 않는다.
- 제품 복용법은 국내 판매 제품의 현재 라벨·공식 자료를 우선한다. 해외 용법으로 국내 제품 용법을 덮어쓰지 않는다.
- 인기 제품 표현은 현재 확인 가능한 순위·판매·리뷰 등 객관 자료가 있을 때만 쓰고 확인일을 남긴다.
- 연구기간은 효과 보장기간이 아니다. 다만 독자가 언제 첫 점검을 할지 판단할 수 있도록 관찰 시점·재평가 시점을 실천 정보로 바꿔 설명한다.
- 연구 설계 용어·표본수·통계값은 결론의 신뢰도와 적용 대상 판단에 필요한 만큼만 남긴다. 같은 근거를 `무작위·대조군·표본수·통계값`으로 반복 나열하지 말고, 독자가 필요한 변화량·기간·대상·행동을 우선한다.
- 출처는 문장 뒤 간결한 링크 또는 하단 자료 출처로 연결한다.

## 7. 쉬운 전문성·정보 밀도·문체
- 기본 독자는 영양학 전공자나 석·박사 전문가가 아닌 **한국 일반 독자**다. **중학생~고등학생이 한 번 읽고 핵심 뜻을 이해할 수 있는 난이도**를 기본값으로 한다.
- **본문·제목·H2·표·핵심카드에서 대중이 아는 한국어를 기본값으로 쓴다.** 전문용어·영문·학명·균주명은 없어도 의미와 정확성이 유지되면 아예 쓰지 않는다.
- 전문용어가 꼭 필요할 때만 `쉬운 한국어(전문용어·영문)` 순서로 첫 등장 한 번 설명한다. 전문용어를 먼저 쓰고 뒤에 번역하는 순서를 기본으로 하지 않는다.
- 독자가 전문용어를 다시 검색하지 않아도 이해돼야 한다. `전구체`는 `몸에서 다른 성분으로 바뀌는 재료`, `상피세포`는 `피부와 점막을 이루는 세포`처럼 먼저 이해되는 말을 쓴다.
- `RAE`, `AREDS2`, `RDA`, `UL` 같은 약어·전문 단위는 독자의 실제 선택에 꼭 필요한 경우만 사용한다. 필요 없으면 본문에서 제거하고 출처·근거에만 남길 수 있다.
- 연구 설계명·균주명·학명·가공 공정명이 결론 이해에 필요하지 않으면 본문에서 빼고 `사람 연구`, `유산균 발효`, `숙성`, `말린 형태`처럼 단순화한다.
- **검색 키워드와 독자 질문이 중심이다.** 알릴시스테인 글이면 독자가 알고 싶은 `일반 마늘·흑마늘·숙성/발효 마늘` 같은 대중적 범주를 먼저 설명하고, 실험실 시료 이름 자체를 정보의 중심으로 만들지 않는다.
- 단순화 때문에 사실이 달라져서는 안 된다. 대중적인 단어가 연구 시료와 정확히 일치하지 않으면 가장 가까운 정확한 쉬운 말을 쓰고, 필요한 차이만 한 문장으로 설명한다.
- 한 문장에는 가능하면 핵심 개념 하나와 중요한 숫자 하나 정도만 둔다. 전문용어·약어·환산식·예외 조건을 한 문장에 여러 개 겹쳐 독자가 다시 읽게 만들지 않는다.
- 쉬운 문체를 위해 정보를 삭제하지 않는다. **정보량은 유지하되 표현 순서를 `쉬운 결론 → 필요한 숫자·조건 → 꼭 필요한 경우에만 전문 근거`로 바꾼다.**
- 본문·표·캡션의 식품·식물·성분명은 한국어 통용명을 먼저 쓴다. 국내 통용명이 있는데 영어만 쓰지 않는다. 고유 제품명처럼 원문 유지가 필요한 경우에도 가까운 곳에서 한국어로 뜻을 알 수 있게 한다.
- 한 문단에는 핵심 답 1개를 두고 2~4문장 안에서 `답 → 이유·수치 → 행동`까지 끝낸다.
- 확인된 효능·장점부터 쓴다. “의미 없다·근거 없다·믿지 마라” 같은 부정 문장을 반복해 글의 중심을 바꾸지 않는다.
- 효능은 `무엇이 좋아지는가 → 어떤 사람이 해당하는가 → 어느 정도·언제 확인됐는가 → 나는 어떻게 활용하는가` 순서가 기본이다.
- 연구명·표본수·통계값·기전을 나열하기보다 독자가 선택에 필요한 수치와 조건을 남긴다.
- 같은 수치를 도입·본문·FAQ에 반복하지 않는다. FAQ는 실제 검색 질문에 직접 답한다.
- 실제 안전 경고는 유지하되 관련 H2 또는 ⑥에 모은다. 긍정적 문체를 이유로 금기·상호작용·응급 행동을 삭제하지 않는다.

## 8. 상단 `핵심만 먼저` 6카드 디자인
- 이 디자인은 사용자 승인 완료된 영양소 기본 상단 요약 형식이다. 신규와 direct/SP1 전체 수정에서 기본값으로 사용한다.
- 위치는 `대표 이미지 → 짧은 도입 → 핵심 요약 카드 → ①번 H2` 순서다.
- 카드 순서는 **효능 / 누가 / 복용 / 기간 / 조합 / 주의** 6개로 고정한다.
- 각 카드는 한 가지 답만 담는다. 상세 연구명·긴 기전·출처 설명·여러 예외 조건을 넣지 않는다. 본문을 읽지 않아도 30초 안에 핵심 선택 기준이 보여야 한다.
- `효능`은 대표 효능·작용, `누가`는 ②에서 효능으로부터 도출한 사람, `복용`은 ③의 실제 하루량·몇 알·횟수, `기간`은 첫 점검 시점, `조합`은 ⑤의 대표 조합 1~2개, `주의`는 ⑥의 가장 중요한 안전 행동을 압축한다.
- **상단 카드의 시각적 우선순위는 건강 개선에 직접 도움이 되는 `효능 → 누가 → 복용·조합`이 먼저다. `주의` 카드는 내용을 숨기지 않되 일반적인 경고·금기만으로 형광펜이나 최고강조를 차지하게 하지 않는다.** 즉시 중대한 위해를 막아야 하는 응급 행동·절대적 금기처럼 독자가 먼저 보지 않으면 위험한 경우만 예외로 최고강조를 사용할 수 있다.
- 공식 권장량이나 상한이 없는 성분은 빈칸으로 두지 말고 “공식 권장량 없음·제품 라벨 우선”처럼 사실대로 요약한다.
- 상단 카드의 숫자·제품·기간·조합은 본문과 정확히 일치해야 한다. 카드에만 있는 새로운 주장·제품·수치를 만들지 않는다.
- source HTML은 공통 렌더러가 인식하도록 다음 의미 구조를 사용한다.
  `<blockquote><strong>핵심만 먼저:</strong> <strong>효능</strong> ...<br><strong>누가</strong> ...<br><strong>복용</strong> ...<br><strong>기간</strong> ...<br><strong>조합</strong> ...<br><strong>주의</strong> ...</blockquote>`
- 각 글에 inline CSS를 새로 넣지 않는다. 공통 `publishing/direct-design.mjs`가 PC에서는 2열, 모바일에서는 1열 카드로 렌더링하며 `QUICK GUIDE · 핵심 요약 · 30초 안에 보는 핵심 기준` 디자인을 사용한다.
- 하단에 같은 내용을 반복하는 `핵심 정리` H2는 만들지 않는다. 본문은 6개 H2 뒤 FAQ와 자료 출처로 마무리한다.

## 9. 강조·이미지·내부링크
- 기존 공통 direct-design 렌더러·CSS·표·카드·PC/모바일 배치를 사용한다. 승인된 핵심 요약 카드도 공통 렌더러를 사용한다.
- 강조는 strong → mark>strong → mark>u>strong이며 공통 누락 방지 하한은 strong18·mark8·mark>u>strong2다. 이 하한은 **강조 누락 방지용 구조 기준이지, 경고 문장이나 중요도가 낮은 숫자를 억지로 끌어올리는 배분 목표가 아니다.**
- **강조를 고르는 첫 기준은 긍정/부정이 아니라 `현재 H2의 질문에 가장 직접 답하는가`이다.** 먼저 H2의 핵심 답을 잡고, 그 안에서 독자의 건강 개선·선택·복용에 가장 도움이 되는 문장을 더 강하게 보이게 한다. 긍정적인 실천 팁이라는 이유만으로 H2의 핵심 답보다 보조 정보를 더 강하게 강조하지 않는다.
- **strong**은 정의·핵심 수치·보조 설명처럼 읽을 때 잡아둘 정보에 사용한다.
- **mark>strong**은 현재 H2의 핵심 답 가운데 확인된 효능·권장 대상·실제 섭취량·복용 시간·기간·조합 이유처럼 독자가 건강 개선 행동으로 바로 옮길 정보를 우선한다.
- **mark>u>strong**은 그 글에서 가장 중요한 건강 개선 효능 또는 실천 행동에 우선 사용한다. 일반적인 부작용·주의·상한·금기는 보통 strong으로 충분하며, 즉시 중대한 위해를 막아야 하는 응급 행동·절대적 금기만 예외적으로 최고강조를 사용할 수 있다.
- **⑥처럼 결핍·과다 자체가 H2의 질문인 절에서는 결핍 예방·대표 결핍 증상·과다 위험·상한·중단 기준이 바로 핵심 답이다.** 이런 내용은 위험·부작용이라는 이유만으로 자동으로 강조를 낮추지 않는다. 그 절에서 독자 판단에 가장 중요한 답이면 mark를 사용할 수 있으며, 마지막의 일반적인 생활 팁이나 라벨 확인 문장이 핵심 답을 밀어내지 않게 한다.
- 형광펜 색은 노란색 한 종류에 고정하지 않는다. **색은 중요도를 정하는 장치가 아니라 의미를 빠르게 구분하는 보조 장치**이며, H2 핵심 답 우선 원칙을 먼저 적용한 뒤 톤을 고른다.
- 공통 렌더러가 지원하는 기본 톤은 `positive / info / caution / negative`다. source에서는 `<mark data-tone="positive"><strong>...</strong></mark>`처럼 지정하며 최고강조도 `<mark data-tone="positive"><u><strong>...</strong></u></mark>`처럼 같은 `data-tone`을 사용한다.
- `positive`는 확인된 효능·개선 결과·권장 행동 등 긍정적 건강 가치에 사용하고 연녹색으로 표시한다. `info`는 권장량·복용 시간·기간·중립적 선택 기준 등 정보성 내용에 사용하고 연파랑으로 표시한다. `caution`은 상한·상호작용·주의 행동처럼 주의가 필요한 내용에 사용하고 연주황으로 표시한다. `negative`는 실제 부작용·과다 위험·중단 기준처럼 명확한 위해 정보에 사용하고 연분홍/적색 계열로 표시한다.
- class 없는 기존 `<mark>`는 하위 호환을 위해 기존 노란색을 유지한다. 새 글·전체 최신화에서는 한 글을 노란색 하나로 도배하지 않고 **내용에 실제로 존재하는 의미 범위에서 2~4개 톤을 자연스럽게 섞을 수 있다.** 다만 색 종류를 채우기 위해 없는 위험·효능·주의를 만들거나 모든 톤을 의무적으로 사용할 필요는 없다.
- 같은 성격의 문장은 같은 톤을 우선해 독자가 색의 의미를 예측할 수 있게 하고, 한 문단에서 여러 색을 난잡하게 섞지 않는다. 임의 HEX·inline style을 원고마다 추가하지 않고 공통 렌더러의 승인 톤만 사용한다.
- 같은 환산식·권장량·주의문을 도입·카드·본문에서 반복해 형광펜 처리하지 않는다. 한 번 강하게 강조했으면 다른 위치에서는 일반 문장이나 strong으로 낮춘다.
- **안전 경고를 mark·mark>u>strong 하한을 채우는 수단으로 사용하지 않는다.** 건강 개선 정보로 하한을 채울 수 없는 주제라면 사실이나 효능을 만들지 않고, 실제 의미가 있는 강조만 사용한다.
- 신규 및 전체 수정은 서로 다른 본문 이미지 최소 3개를 사용한다. HTTPS·alt·원출처·저작자·라이선스·중복을 확인한다.
- imageReview 허용 키와 visualChecked 규칙은 공통 direct 계약을 따른다. visualChecked는 실제 현재 revision의 시각 확인 없이 true로 복사하지 않으며 필수 게이트가 아니다.
- 실제 관련 글만 내부링크한다.

## 10. 작성·검토·공통 검사
- 흐름은 `검색 의도·중복 → 독자 질문 → 근거 조사 → 6개 H2 → 상단 6카드 요약 → 본문·강조·사진·링크 → 내용 검토 → Gate 0 → 저장 확인 → 실행 → 공개 확인`이다.
- 기존 글 전체 최신화에서는 **6개 H2 골격을 먼저 새로 만든 뒤** 기존 글에서 재사용할 사실·출처·이미지 자산만 최신성 확인 후 옮긴다. 기존 H2와 문단을 먼저 복사한 뒤 고치는 방식은 사용하지 않는다.
- 상단 요약은 본문 근거가 정리된 뒤 최종 수치와 표현을 압축해 작성한다. 먼저 카드를 써놓고 본문을 거기에 억지로 맞추지 않는다.
- 저장 전 특히 ② 대상이 효능과 실제 사람 근거에서 직접 나왔는지, ③의 첫 점검 시점이 실제 관찰시점·시험기간과 연결되는지, **④가 TOP7을 우선하되 근거 개수에 따라 TOP5·TOP3로 유연하게 줄였는지, 같은 기준·단위를 유지했는지, 표의 이름이 일반 독자가 이해하는 정확한 한국어인지**, ⑤가 영양소+영양소 조합이며 직접 사람 복합 근거와 기전 설명을 구분했는지, ⑥에 제품 선택이 중복되지 않았는지, 상단 6카드가 본문과 일치하는지 확인한다.
- **같은 `내용 검토`에서 문장 난이도도 한 번만 본다.** 제목·H2·핵심카드·표와 각 H2 첫 답을 먼저 보고, 일반 독자가 한 번 읽고 이해할 수 있는지 확인한다. 전문용어·영문·학명·균주명·연구 가공명이 없어도 정확한 경우에는 삭제하고 대중적인 한국어로 바꾼다. 정보·근거·안전 기준을 줄이지 않는다. 별도 가독성 점수·자동 차단기·자동 재작성 루프는 만들지 않으며 Gate 0·preflight·공개 검증에서 같은 문체 검토를 반복하지 않는다.
- **같은 `내용 검토`에서 강조도 한 번만 본다. 각 H2에서 가장 강한 강조가 그 H2의 질문에 직접 답하는 핵심 문장인지 먼저 확인하고, 그다음 효능·대상·섭취법·조합 같은 건강 개선 정보가 우선되는지와 일반 경고가 글 전체 최고강조의 중심이 되지 않는지만 본다.** ⑥처럼 위험·결핍이 질문 자체인 절은 해당 핵심 답을 위험 정보라는 이유로 감점하지 않는다. 색상은 같은 검토 안에서 의미와 톤이 어긋나지 않는지만 함께 보고 별도 검사 단계는 만들지 않는다. 이 강조 의미 검토를 Gate 0·preflight·공개 검증에서 다시 반복하지 않는다.
- **전체 최신화의 ①~⑥ 의미 대조는 이 `내용 검토` 단계에서 한 번만 한다.** Gate 0·preflight·공개 검증에서 같은 의미 검토를 반복하지 않는다. 이후 단계는 저장 무결성·기술 계약·공개 반영만 확인한다.
- 공통 direct 렌더러의 승인 카드 구조는 회귀 테스트로 보호한다. 자동 의미 판정·자동 재작성 루프는 추가하지 않는다.
- 구조 PASS는 의학적·시각적 검토 인증이 아니다.

## 11. Gate 0·GitHub 저장
- GitHub 쓰기 전에 완성 JSON 전체와 sourceId·articleId·title·digest·검사 상태를 보존한다.
- 실제 commit SHA에 고정한 파일을 다시 읽고 digest가 일치해야 GITHUB_SOURCE_CONFIRMED다.
- WRITE_BLOCKED·파일 부재·조회 불가·내용 불일치를 구분한다.
- 재개할 때는 같은 source의 저장·원장·실행 상태부터 확인하며, 불명확한 저장을 새 ID로 무조건 중복 제출하지 않는다.

## 12. 표준 실행·공개 검증·복구
- 영양소 저장소 저장만으로 발행 완료라고 하지 않는다.
- 동일 원고를 공통 러너에 접수·확인한 뒤 신규는 publish-posts.yml, 기존 수정은 direct-author-update.yml → update-posts.yml을 사용한다.
- 자동 실행과 수동 실행을 겹치지 않는다. 실제 제출 후 최종 상태까지 source와 실행 코드를 바꾸지 않는다.
- **제출 전 실패·취소**이고 `submitting` 원장이 없으며 제출 단계가 시작되지 않았다면, 실패한 단계의 로그를 한 번만 확인해 원인을 직접 수정하고 같은 source로 즉시 재실행한다. 원고·근거·Gate 0·이미 PASS한 검사를 변경 근거 없이 반복하지 않는다.
- 직접 원인이 확인된 장애에는 우회 게이트나 중복 점검 규칙을 추가하지 않고 원인 코드부터 고친다. 같은 증거를 두 번·세 번 재확인해 시간을 쓰지 않는다.
- HTTP200·SUBMIT_CLICKED·Actions SUCCESS만으로 완료라고 하지 않는다. 해당 source의 PUBLIC_VERIFIED와 신규 published/기존 updated 원장을 확인한다.
- PUBLIC_VERIFIED는 공개 반영·렌더 검증이지 의학적 인증이 아니다.
- 제출 후 상태가 불명확하면 재제출하지 않고 기존 읽기 전용 복구 경로를 사용한다.

## 13. 보고·변경 보호
- 작성·내용 검토·기술 검사·GitHub 저장 확인·실행·제출·공개 검증을 구분한다.
- 확인하지 않은 결과를 PASS라고 하지 않는다. 최종 source SHA·Run·공개 URL·원장 상태·중요한 문제만 간결하게 보고한다.
- 승인 없는 reset·force push·중복 발행·URL/카테고리·스킨·광고 변경을 하지 않는다.
- 기존 사용자 변경·과거 원고·원장을 보존한다.
- 검색 색인·유입·광고 성과는 별도 실제 자료로 판단한다.
