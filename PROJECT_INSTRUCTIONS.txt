## 2. 요청 해석·범위
- 일반 독자가 “왜 먹는가, 나에게 필요한가, 얼마를 언제 얼마나 오래 먹는가, 무엇과 같이 먹는가”를 빠르게 이해하게 한다.
- 주제만 입력하면 `조사 → 중복 확인 → 완성 원고 → 표준 발행 → PUBLIC_VERIFIED`까지 요청한 것으로 본다. 원고만·조사만·미리보기만 요청하면 발행하지 않는다.
- 동일 검색 의도의 기존 글은 숫자 URL·articleId를 유지해 전체 최신화한다. 기존 H2·문단 구조는 골격으로 재사용하지 않고 ①~⑥ 새 골격부터 만든다.
- 삭제·URL 변경·권한 확대·유료 가입·무관한 스킨/광고 변경은 별도 승인 없이는 하지 않는다.

- 비밀번호·OTP·CAPTCHA·쿠키·토큰·인증 헤더를 대화·원고·로그·Git에 노출하지 않는다.

## 4. 검색 의도·구성

- 제목의 약속은 도입과 해당 H2 첫 문장에서 바로 답한다. 실제 검색량 자료가 없으면 검색량·노출률 수치를 만들지 않는다.
- 핵심 H2는 최대 6개, FAQ·자료 출처는 보조 영역이다.
- 위치는 `대표 이미지 → 짧은 도입 → 핵심만 먼저 6카드 → H2 ①`이다. 하단 `핵심 정리` H2는 만들지 않는다.

## 5. 영양소 6개 소주제
### ① 정의·주요 성분·작용
- 성분의 정체, 몸에서 하는 일, 비슷한 성분과 차이를 설명한다.
- 전문용어는 첫 등장에 `쉬운 한국어 + 필요 시 전문용어(영문)` 순서로 한 번만 설명한다.
- 기전은 효능 이해에 필요한 만큼만 남긴다.

### ② 효능·기대 변화·권장 대상·제품 형태
- 확인된 효능부터 쓰고 그 효능에서 권장 대상을 도출한다.
- “건강을 챙기고 싶은 사람” 같은 순환 표현은 금지한다.
- 사람 근거가 있으면 대상·기간·용량·관찰된 변화를 짧게 연결한다. 세포·동물 근거만으로 사람 권장 대상을 만들지 않는다.
- 음식·단일성분·복합제 중 목적과 근거에 맞는 형태를 설명한다.

### ③ 실제 섭취량·복용법·기간·대표 제품
- 공식 권장량·충분섭취량·상한이 있으면 먼저 제시한다. 없으면 제품 표시량과 사람 연구 용량을 구분한다.
- 가능하면 `1회량 / 하루 횟수·알 수 / 시간대·식전후 / 같이 먹기 좋은 시간 / 첫 점검 기간 / 장기 복용 재확인 항목`까지 답한다.
- 첫 점검 시점은 실제 사람 자료의 관찰시점·시험기간을 우선하며 임의 범위를 만들지 않는다. 연구기간은 효과 보장기간이 아니다.
- 국내 판매 대표 제품은 제조사·공식 판매처·식품안전나라 등 현재 자료에서 제품명·1회량·하루 용법·성분량을 확인한다.
- “가장 인기”는 현재 순위·판매·리뷰 등 객관 자료가 있을 때만 쓴다.

### ④ 풍부한 식품 TOP7·평균 함량
- 공신력 있는 동일 DB·동일 기준으로 TOP7을 우선 만든다. 품종·생/조리 상태·가식부·100g 또는 1회량을 명시한다.
- 7개가 안 되면 TOP5, TOP3로 줄인다. 3개도 같은 기준 비교가 어렵다면 순위 없이 확인 가능한 식품과 함량만 설명한다.
- 서로 다른 DB·단위·제품 표시량을 섞지 않는다. 숫자를 채우기 위해 익명 실험시료를 넣지 않는다.
- `평균 함량`은 실제 평균값(mean 등)일 때만 쓴다.
- 높은 함량과 실제 먹는 양을 구분한다.

### ⑤ 함께 섭취할 영양소·보충제 조합
- 음식 궁합보다 `영양소/기능성 성분 + 영양소/기능성 성분`을 우선한다.
- 각 조합은 `A+B → 이유 → 같이 먹는 방법·시간 → 기대 이점 → 중복·상한·약물 주의` 순서로 설명한다.
- 사람 복합 연구가 있으면 전체 조합에서 확인된 결과로 표현하고 단일성분 독립 효과로 바꾸지 않는다.
- 강한 조합이 1~2개뿐이면 그 수만 제시한다. 개수 채우기용 조합 금지.

### ⑥ 결핍·과다 섭취
- 제품 선택을 반복하지 않고 결핍·과다에 집중한다.
- 결핍 증상·위험군·확인 방법, 과다 부작용·상한·중단/상담 기준을 설명한다.
- 결핍증이 정의되지 않은 기능성 성분은 억지로 결핍 질환을 만들지 않는다.
- 응급 증상·중요 금기는 행동 기준을 명확히 쓴다.

## 6. 조사·근거·수치
- 정부·공식 영양 DB·전문기관·진료지침·원문 연구를 우선한다. 다른 블로그를 근거로 복사하지 않는다.
- 권장량·충분섭취량·상한·연구용량·제품표시량·유효성분량을 구분한다. 원료량을 유효성분량처럼 쓰지 않는다.
- 효능은 사람 근거를 우선한다. 복합제품 결과를 단일성분 효과로 바꾸지 않는다.
- 제품 복용법은 국내 현재 라벨·공식 자료를 우선한다.
- 연구명·표본수·통계값은 독자의 선택에 필요한 수준만 남긴다.
- 출처는 문장 뒤 간결한 링크 또는 하단 자료 출처로 연결한다.

## 7. 문체·정보 밀도
- 한국 일반 독자, 중학생~고등학생이 한 번 읽고 이해할 수준을 기본값으로 한다.
- 제목·H2·표·핵심카드는 대중적인 한국어를 우선한다. 전문용어·영문·학명·균주명은 꼭 필요할 때만 쓴다.
- 한 문단 2~4문장, `답 → 이유·수치 → 행동` 순서로 끝낸다.
- 확인된 효능·장점부터 쓰고 부정·한계 문장을 반복해 글의 중심을 바꾸지 않는다.
- 효능은 `무엇이 좋아지는가 → 누가 해당하는가 → 어느 정도·언제 확인됐는가 → 어떻게 활용하는가` 순서를 기본으로 한다.
- 같은 수치를 도입·본문·FAQ에서 반복하지 않는다. 안전 경고는 관련 H2 또는 ⑥에 모은다.

## 8. `핵심만 먼저` 6카드
- 순서는 `효능 / 누가 / 복용 / 기간 / 조합 / 주의`로 고정한다.
- 각 카드는 한 가지 답만 담고, 상세 연구명·긴 기전·출처 설명·여러 예외를 넣지 않는다.
- 카드 숫자·제품·기간·조합은 본문과 정확히 일치해야 하며 카드에만 새 주장을 만들지 않는다.
- source 구조:
  `<blockquote><strong>핵심만 먼저:</strong> <strong>효능</strong> ...<br><strong>누가</strong> ...<br><strong>복용</strong> ...<br><strong>기간</strong> ...<br><strong>조합</strong> ...<br><strong>주의</strong> ...</blockquote>`
- 각 글에 inline CSS를 넣지 않는다. 공통 `publishing/direct-design.mjs`가 PC 2열·모바일 1열로 렌더링한다.
- 6카드 답변 본문은 PC·모바일 모두 `.quick-summary-item p {font-weight:600}`으로 표시한다. 제목·라벨은 더 강한 기존 굵기를 유지한다.
- `font-weight:600`은 표시 규칙이며 의미 강조 수에 포함하지 않는다. 카드 전체를 strong/mark로 감싸 굵기를 흉내 내지 않는다.
- 구조·반응형 배치·600 굵기는 회귀 테스트로 보호한다.

## 9. 강조·이미지·내부링크
- 강조 단계: `strong → mark>strong → mark>u>strong`.
- 영양소 direct/SP1 최소 하한: `strong25 / mark14 / mark>u>strong8`.
- 하한은 누락 방지용이지 개수 채우기 목표가 아니다. 사실·효능을 만들거나 경고 문장을 억지로 승격하지 않는다.
- TOP7·TOP5·TOP3 순위표가 있으면 1·2·3위를 반드시 강조한다. 1위는 최고강조 우선, 2·3위는 최소 `mark>strong`, 기본 톤은 `info`.
- `mark>u>strong`은 가장 중요한 효능·실천 행동에 우선한다. 일반 주의·상한은 보통 strong으로 충분하며 응급·절대 금기만 예외적으로 최고강조할 수 있다.
- ⑥에서는 결핍·과다 자체가 질문이므로 핵심 위험·상한·중단 기준은 필요하면 mark를 사용할 수 있다.
- 승인 톤은 `positive / info / caution / negative`. 색은 중요도가 아니라 의미 구분용이다. 임의 HEX·inline style 금지.
- 신규·전체 수정은 서로 다른 본문 이미지 최소 3개. HTTPS·alt·원출처·저작자·라이선스·중복을 확인한다.
- `visualChecked`는 실제 현재 revision 시각 확인 없이 true로 복사하지 않는다.
- 실제 관련 글만 내부링크한다.

## 10. 작성·검토
- 흐름: `검색 의도·중복 → 독자 질문 → 근거 조사 → 6개 H2 → 6카드 → 본문·강조·이미지·링크 → 내용 검토 → Gate 0 → 저장 확인 → 실행 → 공개 확인`.
- 전체 최신화는 새 6개 H2 골격부터 만들고 기존 글에서는 최신성 확인된 사실·출처·이미지 자산만 옮긴다.
- 내용 검토에서 ② 대상-효능 연결, ③ 복용·기간, ④ 동일 기준 TOP7/5/3, ⑤ 직접 복합근거 구분, ⑥ 결핍·과다 집중, 카드-본문 일치를 확인한다.
- 같은 내용 검토에서 문장 난이도와 강조 의미도 한 번만 본다. Gate 0·preflight·공개검증에서 같은 의미 검토를 반복하지 않는다.
- 자동 의미 판정·자동 재작성 루프는 추가하지 않는다. 구조 PASS는 의학적·시각적 인증이 아니다.

## 11. Gate 0·GitHub 저장
- GitHub 쓰기 전에 완성 JSON, sourceId·articleId·title·digest·검사 상태를 보존한다.
- 실제 commit SHA에 고정한 파일을 다시 읽고 digest가 일치해야 `GITHUB_SOURCE_CONFIRMED`다.
- WRITE_BLOCKED·파일 부재·조회 불가·내용 불일치를 구분한다.
- 재개 시 같은 source의 저장·원장·실행 상태부터 확인하고 불명확한 저장을 새 ID로 중복 제출하지 않는다.

## 12. 실행·공개검증·복구
- 영양소 저장소 저장만으로 발행 완료라고 하지 않는다.
- 신규: `publish-posts.yml`; 기존 수정: `direct-author-update.yml → update-posts.yml`.
- 자동·수동 실행을 겹치지 않는다. 실제 제출 후 최종 상태까지 source와 실행 코드를 바꾸지 않는다.
- 제출 전 실패이고 `submitting` 원장이 없으면 원인 로그를 한 번 확인해 직접 원인을 수정하고 같은 source로 재실행한다. 이미 PASS한 검사를 근거 없이 반복하지 않는다.
- HTTP200·SUBMIT_CLICKED·Actions SUCCESS만으로 완료라 하지 않는다. 해당 source의 `PUBLIC_VERIFIED`와 신규 `published`/기존 `updated` 원장을 확인한다.
- 제출 후 상태가 불명확하면 재제출하지 않고 기존 읽기 전용 복구 경로를 사용한다.

## 13. 보고·변경 보호
- 작성·내용검토·기술검사·GitHub 저장확인·실행·제출·공개검증을 구분한다.
- 확인하지 않은 결과를 PASS라고 하지 않는다.
- 최종 source SHA·Run·공개 URL·원장 상태·중요 문제만 간결하게 보고한다.
- 승인 없는 reset·force push·중복 발행·URL/카테고리·스킨·광고 변경 금지.
- 기존 사용자 변경·과거 원고·원장은 보존한다.
